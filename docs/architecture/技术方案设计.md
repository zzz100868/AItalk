# 赛博聊机 · 技术方案设计

**版本**：v0.3
**状态**：按当前实现校准（2026-07-12）
**详细入口**：[后端架构](后端架构.md) · [前端架构](前端架构.md) · [API 总览](../api/README.md) · [当前进度](../DEV_PROGRESS.md)

## 1. 目标与边界

赛博聊机通过 AI 文字/语音对话持续形成用户画像，再按固定周期为用户生成匹配结果。当前仓库的 MVP 范围包括：

- 微信小程序登录、资料、语音通话、记忆库、匹配、通知和解锁入口。
- NestJS HTTP API、PostgreSQL 持久化、LLM 文字聊天、画像抽取、匹配与支付/通知代码。
- 独立 WebSocket 语音网关，负责 ASR、TTS、对话编排和画像证据。

广场、关注关系、账号安全、完整设置中心、语音历史页面和生产运营后台不在当前实现范围。

## 2. 当前系统架构

```text
微信小程序
  ├─ HTTP/JSON -> NestJS 主服务 (:3000/api)
  │                ├─ Auth/Profile/Memory
  │                ├─ Match/Notifications/Pay
  │                ├─ LLM adapter
  │                └─ Prisma -> PostgreSQL
  └─ WebSocket -> 语音网关 (:3001/ws/voice)
                   ├─ VoiceSession
                   ├─ ASR / TTS adapter
                   ├─ probe_card / coverage / evidence
                   ├─ LLM orchestration
                   └─ Prisma -> 同一 PostgreSQL
```

主服务和语音网关是两个进程，共享 `DATABASE_URL` 和 `JWT_SECRET`。当前没有内部 HTTP、Redis 或消息队列；语音网关直接访问数据库。

## 4. 领域模块

### 4.1 身份与资料

前端启动时使用 `wx.login`，HTTP 服务签发 JWT。当前后端仍生成 mock openid，因此真实微信身份和实名状态是上线阻塞项。

资料基础字段已通过 `/api/me` 对接。照片墙后端记录接口存在，但二进制上传和前端权威来源未完成。

### 4.2 Memory

文字消息写入 `memory_chat_messages`，LLM 未配置时使用服务端预置回复。每累计 5 条用户消息后，进程内定时任务尝试抽取画像并写入 `profile_documents`、`memory_insights`。

这套抽取逻辑与语音证据逻辑尚未共享模块；后续应统一画像 schema、置信度和纠正规则。

### 4.3 Voice

语音网关协议和编排详见 [对话编排设计](对话编排设计.md) 与 [Voice API](../api/voice.md)。当前采用 30 张版本化 probe_card、10 维 coverage checklist 和逐条 evidence 持久化。

已实现代码不等于真实服务已验收。生产前必须完成最新迁移和真实 ASR/TTS/LLM 的 15 分钟整通。

### 4.4 Match

每周 Cron 预生成轮次。候选池基于最近活跃、画像置信度、性别/取向、年龄、城市和最近配对历史过滤，使用四项加权得分与贪心配对。详情见 [匹配算法设计](匹配算法设计.md)。

`POST /api/match/do` 只读取预生成结果，不即时运行匹配。

### 4.5 Notifications

站内通知已持久化。匹配和支付事件会写通知；微信订阅消息是 best-effort 外部发送。当前订阅授权接口不持久化，尚未形成完整推送闭环。

### 4.6 Payment

解锁使用 `orders` 和 `entitlements`。代码包含微信支付 V3 下单和回调处理，但真实商户链路未验收，多表写入也尚未纳入事务。

## 5. 数据模型

当前 Prisma 模型：

| 领域 | 模型 |
|---|---|
| 用户 | `User`、`UserPhoto`、`UserSettings` |
| Memory | `MemoryChatMessage`、`MemoryInsight`、`ProfileDocument` |
| Voice | `VoiceSession`、`DialogueTurn`、`VoiceCoverageState`、`VoiceEvidence` |
| Match | `MatchRound`、`MatchResult`、`MatchFeedback` |
| Payment | `Order`、`Entitlement` |
| Notifications | `Notification` |

`ProfileDocument.data` 是当前画像汇总载体，`VoiceEvidence` 是语音证据来源。目标态曾规划 `questions`、`dimensions`、`long_term_memories` 和 pgvector，但当前 schema 没有这些模型或扩展。

## 6. 外部依赖与降级

| 外部能力 | 当前 adapter | 未配置时行为 |
|---|---|---|
| 微信登录 | 尚未接真实接口 | 生成 mock openid |
| 火山 LLM | Ark Chat Completions | 文字返回预置回复；语音按标准卡片推进 |
| 火山 ASR | WebSocket | 使用 mock ASR/VAD 路径 |
| 火山 TTS | 双向 WebSocket | 只下发文本，短延时后结束回合 |
| 微信支付 | V3 JSAPI | 创建 pending mock order，不产生真实权益 |
| 微信订阅消息 | REST API | 缺模板/凭据时跳过 |

降级路径只能支持开发和演示，不应作为真实功能验收证据。

## 7. 一致性与安全边界

- HTTP 和语音网关必须使用相同 `JWT_SECRET`；生产环境禁止默认 secret。
- 支付回调、权益、匹配解锁和通知需要事务与幂等保护。
- 匹配轮次、结果和通知需要明确失败恢复策略。
- 用户画像和语音证据属于敏感数据，需要访问控制、删除策略和日志脱敏。
- API 输入当前缺少完整 DTO 校验，生产前需要补齐。
- 前端 mock fallback 不得隐藏写操作失败或生产配置错误。

## 8. 构建与部署现状

主服务和语音网关有独立构建/启动脚本，详见 [开发指南](../DEVELOPMENT.md)。仓库当前没有 Docker、Compose、Nginx、CI/CD、限流、监控或集中日志配置。

生产拓扑至少需要：HTTPS/WSS 入口、两个受守护的 Node.js 进程、PostgreSQL、密钥管理、数据库迁移、日志告警、备份和回滚。Redis/Bull/pgvector 只有在明确需求出现后再引入，不能按旧目标态默认视为依赖。

## 9. 当前优先级

1. 真实微信身份与数据库迁移基线。
2. 前后端 userId、照片、洞察和通知授权契约。
3. 语音、匹配、支付、订阅消息的外部集成验收。
4. 事务、幂等、输入校验和集成测试。
5. CI、部署、监控、限流和上线工程。

准确状态和待确认事项见 [当前开发进度](../DEV_PROGRESS.md)。

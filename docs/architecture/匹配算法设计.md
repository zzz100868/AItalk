# 匹配算法设计

**状态**：当前代码实现（2026-07-12）
**实现**：`server/src/match/matching.engine.ts`、`server/src/match/match.service.ts`
**接口**：[Match API](../api/match.md)
**画像来源**：[66 题维度映射](../product/66题维度映射.md)

## 1. 执行方式

`MatchScheduler` 每周二调用 `executeMatchRound()`：创建轮次、构建候选池、计算所有合法 pair、贪心配对、生成文案、写结果与站内通知，最后发布轮次。

用户点击“开始匹配”时，`POST /api/match/do` 只读取当前周已生成结果，不现场执行算法。前端请求失败时会回落到本地 mock 候选人。

## 2. 候选池

服务先查询 `updatedAt` 在最近 7 天内且有 `profileDoc.dimensions` 的用户。

高权重维度：

```text
marriage_orientation
family_model
values_core
conflict_fear
communication_style
```

正常期要求至少 3 个高权重维度置信度 `>= 0.4`；活跃用户少于冷启动阈值时降为 `>= 0.2`。当前代码没有把 `realNameVerified` 作为候选硬条件，也没有封禁字段。

活跃度：

```text
activity = 0.5 * min(voice_sessions_7d, 10) / 10
         + 0.5 * min(memory_chat_messages_7d, 50) / 50
```

## 3. Pair 硬条件

`filterCandidatePair()` 当前依次检查：

1. 不能是同一用户。
2. 双方性别和取向有数据时必须兼容；数据缺失时放行。
3. 年龄差正常期不超过 5 岁，冷启动不超过 8 岁；数据缺失时放行。
4. 正常期要求同城，冷启动不要求；城市缺失时放行。
5. 过去 28 天已经匹配过的 pair 不再匹配。

## 4. 得分

```text
match_score = 0.40 * complementary
            + 0.25 * interest_overlap
            + 0.25 * stage_fit
            + 0.10 * activity_bonus
```

最终乘以 100 并四舍五入。

### 4.1 维度分

只使用双方都存在且置信度 `>= 0.2` 的维度：

- `similar`：`1 - abs(A.score - B.score)`
- `complementary`：`abs(A.score - B.score)`
- `mixed`：60% 相似 + 40% 互补

没有可用维度时回落为 `0.5`。

### 4.2 兴趣重合

当前实现直接对 `interest_map.evidence[].text` 小写化后做集合 Jaccard。没有兴趣证据时回落 `0.5`。这是一种严格文本相等，尚未使用分词、标签归一或向量相似度。

### 4.3 阶段适配

使用 `marriage_orientation.score` 的相似度；缺失时回落 `0.5`。

### 4.4 活跃度

取双方 activity score 的较小值，避免一方高活跃掩盖另一方低活跃。

## 5. 配对

对所有合法 pair 计算分数并降序排列，依次选择双方都未被使用的 pair。冷启动时，剩余用户再按当前顺序两两配对；如果人数为奇数，最后一人没有结果。

当前不是 Gale-Shapley，也没有全局最优保证。

## 6. 文案

每对用户调用 LLM JSON 输出：`reason`、两条 `icebreakers`、`insight`。LLM 未配置或输出不完整时使用固定规则文案。

`MatchResult` 实际保存 `reasonText`、`icebreakers` 和 `insightText`；当前 HTTP 响应没有返回 `reasonText`，前端展示的是 `insight` 和 icebreakers。

## 7. 反馈

反馈接口写入 `MatchFeedback`。只有 `negative` 且存在 `skipReason` 时，服务通过进程内 `setTimeout` 尝试调整用户画像。该任务没有队列、重试或幂等保证，前端当前也没有反馈 UI。

## 8. 已知风险与待验证

- 候选过滤依赖 `User.updatedAt`，登录或聊天是否更新该字段需要用真实数据验证。
- 冷启动阈值和维度权重是代码常量，没有离线评估数据。
- 兴趣 Jaccard 使用原始证据全文，重合率可能长期接近 0。
- 每周轮次、结果和通知不是事务写入，失败后可能留下部分数据。
- 缺少至少两个真实画像用户的数据库集成测试。
- 实名、封禁、隐私和用户主动参与匹配尚未纳入候选条件。

## 9. 后续方向

先补候选池/配对集成测试和指标，再讨论稳定婚配、向量兴趣相似度、反馈学习或每周多结果。任何算法升级都应保留当前 HTTP 字段契约或同步更新前端。

# 赛博聊机 · 后端架构与交接

**状态**：当前实现校准（2026-07）
**适用范围**：`server/`、`server/voice-gateway/`、Prisma schema、后端对前端接口契约
**上游文档**：[技术方案设计](技术方案设计.md) · [API 总览](../api/README.md) · [测试与验收](../TESTING.md)

本文是后端接手入口。它描述当前代码实际形态，不替代 `docs/api/` 的接口细节，也不替代 `docs/DEV_PROGRESS.md` 的阶段推进记录。

## 1. 当前运行形态

后端由两部分组成：

| 进程 | 路径 | 启动命令 | 职责 |
|---|---|---|---|
| NestJS 主服务 | `server/src/` | `cd server && npm run start:dev` | HTTP API、JWT 鉴权、Prisma 数据访问、LLM 文字聊天、匹配、支付、通知 |
| 语音网关 | `server/voice-gateway/` | `cd server && npm run start:voice` | WebSocket 语音会话、ASR/TTS 对接、语音对话编排、通话记录写入 |

主服务和语音网关共享：

- `DATABASE_URL` 指向同一个 PostgreSQL。
- `JWT_SECRET` 表示同一个用户身份语义。
- `profile_documents`、`voice_sessions`、`dialogue_turns` 等 Prisma 表结构。

当前语音网关不是 Nest Module；它是独立 Node.js WebSocket 进程，直接读取环境变量、验 JWT、创建 PrismaClient 单例并写数据库。

## 2. 主服务模块边界

`server/src/app.module.ts` 汇总以下模块：

| 模块 | 路径 | 主要职责 | 当前边界说明 |
|---|---|---|---|
| Auth | `server/src/auth/` | `POST /api/auth/wx-login`、JWT 签发、HTTP AuthGuard | 当前仍是 mock openid，生产前必须接微信 `jscode2session` |
| Profile | `server/src/profile/` | 当前用户资料、照片墙、用户主页 | `GET /users/:author/home` 当前按 user id 查询，前端参数语义需和前端负责人定稿 |
| Memory | `server/src/memory/` | 文字聊天、洞察、人格档案、画像抽取触发 | 与语音网关存在对话编排/画像抽取逻辑重复 |
| Match | `server/src/match/` | 每周匹配、匹配结果、反馈、匹配通知 | 匹配轮次写入和通知写入目前不是事务边界 |
| Notifications | `server/src/notifications/` | 通知列表、已读、清空、订阅消息推送 | 订阅消息发送是 best-effort，不应阻塞核心业务 |
| Pay | `server/src/pay/` | 微信支付下单、回调、权益解锁 | 支付成功后的多步写入应收敛到事务 |
| LLM | `server/src/llm/` | 火山 Ark Chat Completions 封装 | 当前无统一 timeout/retry/circuit breaker |
| Prisma | `server/src/prisma/` | 全局 PrismaService | DB 不可用时只保证 `/health` 可用，业务 CRUD 仍会失败 |
| Health | `server/src/health/` | `GET /api/health` | 运维/本地启动检查 |

当前主服务分层是 `Controller -> Service -> PrismaService`。这对 MVP 足够直接，但后续涉及多表一致性、领域规则复用或跨进程共享时，应优先抽深模块，而不是继续把逻辑堆进 Service。

## 3. 数据模型现状

Prisma schema 当前覆盖：

- 用户域：`User`、`UserPhoto`、`UserSettings`
- 记忆域：`MemoryChatMessage`、`MemoryInsight`、`ProfileDocument`
- 语音域：`VoiceSession`、`DialogueTurn`
- 匹配域：`MatchRound`、`MatchResult`、`MatchFeedback`
- 支付域：`Order`、`Entitlement`
- 通知域：`Notification`

目标态文档中提到的 `questions`、`dimensions`、`profile_evidence`、`covered_questions`、`long_term_memories`、`pgvector` 还没有落到当前 Prisma schema。现在画像主要由 `ProfileDocument.data` 的 JSON 承载。

## 4. 语音网关边界

语音网关当前模块：

| 文件 | 职责 |
|---|---|
| `index.ts` | HTTP/WS server、JWT 验证、连接生命周期 |
| `session.ts` | 每个通话会话的状态机、barge-in、计时器、ASR/TTS/LLM 编排 |
| `asr.service.ts` | 火山 ASR WebSocket 协议帧、mock ASR |
| `tts.service.ts` | 火山 TTS WebSocket 协议帧、音频 chunk 事件 |
| `dialogue.service.ts` | 语音对话回复、画像抽取、通话记录写库 |
| `prisma.ts` | 语音网关独立 PrismaClient 单例 |
| `types.ts` | WS 消息类型与 `SessionState` |

主要技术风险：

- `VoiceSession` 是高复杂度状态机，`state` 之外还有 `asrReady`、`ttsCompleted`、`closeAfterTts`、`speechDetected`、`finalizingUserSpeech` 等布尔状态协同。
- ASR/TTS 协议解析依赖外部二进制协议，真实服务异常时需要更明确的错误模型。
- 文字聊天和语音聊天各有一套 `PROBE_HINTS`、prompt 构建、画像合并逻辑，后续容易漂移。

后续优先方向不是重写语音网关，而是先把状态转移显式化，并把 ASR/TTS/LLM 作为 adapter seam。

## 5. 后端对前端的契约边界

你负责后端时，应主动和前端负责人确认以下契约：

| 契约 | 当前情况 | 建议 |
|---|---|---|
| 用户主页参数 | 后端 `GET /api/users/:author/home` 当前把 `author` 当 user id | 定名为 `userId` 或明确支持 handle/nickname，避免继续用模糊 `author` |
| 照片墙 | 后端已有 `/api/me/photos`，前端当前仍偏本地存储 | 定以后端为权威数据源，本地只做展示缓存 |
| Memory insights | 后端已有 update/delete，前端当前可本地改 storage | 定以后端为权威数据源，失败时前端提示同步失败 |
| Mock fallback | 前端保留 mock fallback | 真实接口成功时以后端响应为准；fallback 只作为开发/离线降级 |
| 语音 WS event | `types.ts` 是当前实际消息集合 | 后端维护事件表，前端只按事件更新 UI，不理解后端状态机 |

## 7. 后端优先治理顺序

1. **Auth 真实身份**：用微信 `jscode2session` 替换 mock openid，明确实名状态写入规则。
2. **API/前端契约收敛**：先定 `userId`、photos、insights、notifications、payment 的数据权威来源。
3. **共享对话/画像模块**：收敛 MemoryService 与 voice-gateway DialogueService 的重复编排逻辑。
4. **VoiceSession 显式状态机**：让 ASR/TTS event race 可测试。
5. **事务边界**：支付回调、权益解锁、匹配轮次、通知写入用事务或幂等约束保护。
6. **Harness 状态机**：在当前文档稳定后，再接入 `docs/FEATURES.json` 和 `.harness/config.json`。

## 8. 不要做的事

- 不要把旧 `data/docs/` 恢复为文档入口。
- 不要在根目录再建第二套后端知识库；新增后端文档应挂到 `docs/README.md`。
- 不要用根 `npm test` 判断后端是否通过；当前它是占位失败脚本。
- 不要把前端页面内部重构作为后端任务的一部分；后端只负责接口契约、数据权威来源和验证样例。
